# Implementation Log: Task 9

**Summary:** Added runServerMatch(task, timeoutMs) and recordServerMatchFailure(task, reason) in a new src/lib/mcp/serverMatch/run.ts (design C6): resolves the job and resume scoped to the task's userId at run time, preprocesses both, gets the model, and runs generateText inside withSpan with the shared job-match system/user prompts, TEMPERATURES.FEEDBACK and both the ollama num_ctx and MATCH_PROVIDER_OPTIONS providerOptions under an AbortSignal.timeout. On success it parses scores and calls writeJobMatch with the design matchData shape (surface "server"); a P2025 from the write drops silently. Every failure path (no resume, unreadable job/resume, provider throw, non-"stop" finish, no SCORES line, or the abort-signal timeout) goes through recordServerMatchFailure, which does prisma.job.updateMany({ where: { id, userId } }) and logs one log.error line, dropping silently (no log) when the updateMany count is 0. Amended __tests__/serverMatchRun.spec.ts's four finishReason mocks from plain strings ("stop"/"length") to the LanguageModelV3FinishReason object shape { unified, raw } — the installed ai 6.0.256 reads result.finishReason.unified from doGenerate's return, so a plain string always resolved to undefined, collapsing the "stop" and "length" cases to the same (wrong) outcome; confirmed empirically with a standalone generateText probe against MockLanguageModelV3 before editing.
